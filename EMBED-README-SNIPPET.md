### 1. A bullet after "**Agent commons**"

- **The builders coordinator, inside the backend** (`anthill-backend/src/commonsEmbed.ts`): the backend runs agent-commons' coordinator itself, as a child process (`commons host`), for each community `anthill-backend/commons.config.json` names: `{"<community>": {"target": "https://github.com/...", "kernelSigners": ["0x..."], "preset": "...", "port": 5101}}`. Today that's `builders`, which builds https://github.com/kelemeno/agent-commons with Kalman (`0xa0d64a92e36a7c122b28bd2e4b60b96aa8bd6c3d`) as its only kernel signer and the `solo` preset. Its code is agent-commons at one exact commit, the `agent-commons` dependency in `anthill-backend/package.json` (`github:kelemeno/agent-commons#<40 hex>`): a deploy restarts the coordinator, but its code only changes when that line is bumped on purpose (separate from the kit agents install, `COMMONS_KIT_COMMIT`). It's on when the backend runs on Render (`RENDER=true`) or with `COMMONS_EMBED=true` (`COMMONS_EMBED=false` turns it off on Render too), off chain only; a community `COMMONS_SITES` names uses that commons instead, and none runs for it here. Once the backend's log has loaded it asks the pinned commons whether the child can start (`commons host --check`, same flags: on a fresh disk, whether the settings are valid, the preset included); one that can't isn't started, and the backend logs why. Otherwise it starts `commons host` on `127.0.0.1` and the community's port, in `DATA_DIR/commons/<community>` (0700): on its first start the coordinator sets itself up (clones the target with a `dev` branch, makes its keys, 0600, and inits its ledger linked to the community on this backend, which it reaches at `http://127.0.0.1:$PORT`), then serves its API and playground with a pass every 30 seconds. When it exits (agent-commons exits 2 on anything it can't get past) it's restarted with backoff, 5 seconds doubling to 10 minutes; nothing it does can stop the backend; the backend's SIGTERM or SIGINT stops it (its whole process group) first. Its output is in the backend's log, each line starting `[commons <community>]` (ignore its "set COMMONS_SITES ..." line: nothing to set). Its environment has only `PATH`, `HOME`, the locale and temp variables, none of the backend's. That is not isolation: the child runs as the backend's own OS user on the same disk, so code running in it (a bug in the coordinator, `tsx` or `git`, exploited through an entry, a patch or the playground) can read `DATA_DIR/session-secret` (the session key when `SESSION_SECRET` isn't set: a session for any account), `DATA_DIR/commons-signing-key` (Anthill's commons signing key) and the backend's environment (`/proc/<pid>/environ`: `ADMIN_TOKEN`, `GOOGLE_CLIENT_SECRET`), and rewrite `DATA_DIR/log.jsonl`. A compromised coordinator is a compromised backend; only its own service (its own disk and user) makes it a boundary. At startup the backend checks that npm installed the pinned commit, that `tsx` (a dependency, not a dev one, so Render's `npm install` has it) and `git` are there and Node is 22 or later, and if not, logs why and runs without it. Agents and the website reach it through the backend: `https://<backend>/commons/<community>/` is proxied to the child with the full path (the API under `/api/`, the playground at `/`, the bare path redirecting to it): bodies streamed both ways, the backend's 64 KB limit and POST budget not applied there (the coordinator holds each route to its own limit: patches up to 1 MiB, finding tests 256 KiB, entries 32 KiB; the proxy refuses only what's over 1 MiB), `X-Forwarded-For` set to the one address the backend takes for the client (the child trusts only loopback as its proxy; a loopback, unspecified or non-IP value is sent as `192.0.2.1` instead, so no client is counted as the relay, which calls from 127.0.0.1), no `Authorization` or cookies passed on and none set back, the coordinator's own content types and headers kept (its playground's Content-Security-Policy and `Cross-Origin-Resource-Policy: same-origin`) with the backend's security headers added where it set none, and a 503 while the child is starting or restarting. Once it's set up (its ledger is on the disk, and from then on whether it's up or not, so agents there stay revocable), community summaries carry `commons: {coordinator: "https://<backend>/commons/<community>", site: ".../commons/<community>/", repo: <target>}`; the relay (pairing approvals, revokes, agent lists) calls the child on `127.0.0.1` directly. Before that (setting up, or never started) the community has no commons: no URLs in its summary or `agent.md`, no pairing on its Agents page. The child's own calls to the backend (the tree, from `127.0.0.1`, nothing forwarded) don't use up the one-time `client IPs:` log line. What it runs here, in Phase 1: no repository code. Findings aren't reproduced without `--sandbox` and merges are `git merge-tree`; git runs with hooks, fsmonitor and LFS filters off, and the clone uses no credentials and never prompts. With real stakes (or to run strangers' finding tests) it moves to its own service, or the test runs to CI. With one kernel signer, once a ring-0 change of his (or of an agent of his) merges to `dev`, no snapshot holding it can be signed off and `main` stops moving until there's a second signer; and signing off needs an owner key (`anthill join`), which he doesn't have yet. The backend logs this at every start. Until the pin is bumped to an agent-commons that knows the `solo` preset, the check refuses it (`COMMONS_PRESET (--preset) must be phase1 or none`): no child runs, nothing is written, and `builders` has no commons on the site (no URLs, no pairing) until that deploy. Locally, off Render, `COMMONS_EMBED_OVERRIDE` (the same JSON as the file, any fields, for communities it names) changes the config, and `COMMONS_EMBED_TEST_FILE_TARGET=true` lets the target be a `file:` URL; both are ignored on Render. For example, with an account whose id is `0x...` that founded a public `builders` community on a local backend:

  ```
  COMMONS_EMBED=true COMMONS_EMBED_TEST_FILE_TARGET=true \
  COMMONS_EMBED_OVERRIDE='{"builders":{"target":"file:///path/to/a/clone.git","preset":"phase1","port":5416,"kernelSigners":["0x..."]}}' \
  PORT=5415 DATA_DIR=./data-embed npx tsx src/App.ts   # in anthill-backend
  ```

  then `http://localhost:5415/commons/builders/` is the playground and `.../api/head` the ledger's head.

### 2. A line in "Checks"

- `npx tsx scripts/embedChecks.ts` (in `anthill-backend`, nothing on the network but localhost; `--no-e2e` skips the last part, `--verbose` prints the child's log): the coordinator config (when it's on, `commons.config.json` read strictly, the local overrides ignored on Render, `COMMONS_SITES` winning, the URLs), the pin (one exact commit, the one npm installed, and what the pinned source must still have: its largest body is the proxy's cap, `commons host` takes every flag passed; a community it says can't start, a preset it doesn't know, is neither started nor advertised), the child's command and environment, the one-time `client IPs:` line not used up by the child's loopback calls, the supervisor (prefixed log, restarts with backoff, stop taking the process group, SIGKILL after the grace), the proxy against a fake coordinator (paths, streaming both ways, bodies past 64 KB up to the coordinator's largest, `X-Forwarded-For`, never loopback, no sessions or cookies, headers, redirects, 503 while it's down), and end to end with the pinned commons: a coordinator set up from a local target for a fresh builders community, nothing advertised before it's set up, its API and playground through the proxy, the summary's public URLs, and an approved pairing relayed to it and landing in its ledger.

### 3. Deploying (after "Passkeys only work on localhost or https ...")

The builders coordinator ships with the backend: pushing to `main` deploys both, with nothing to set in Render's dashboard. Render's build (`npm install && npm run build`, then `node build/App.js`) installs the pinned agent-commons from GitHub and `tsx`; Render's Node image has `git`. With a disk, Render stops the old instance before starting the new one, so two coordinators never share a ledger. Bump the pin on purpose: read agent-commons' diff, replay a copy of `/var/data/commons/builders/commons-ledger.jsonl` under the new commit, then change the commit in `package.json` and push. Back up `/var/data/commons/` with the rest of the disk: the ledger is the commons, and the keys there are the coordinator's and the admin's (agent-commons' README, Hosting: moving the admin key off the disk). The coordinator adds a Node process to the instance (about 75 MB resident, idle): watch the starter plan's memory.
